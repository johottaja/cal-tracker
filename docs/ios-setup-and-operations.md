## One-time Apple setup

1. Complete Apple Developer Program enrollment. Accept any pending agreements in Apple Developer and App Store Connect.
2. Run `npm ci`, then `npx eas login` as `johocharger`.
3. Run `npm run build:testflight`. This creates an App Store-distribution binary and automatically submits it to TestFlight. Follow the interactive prompts to sign into Apple and create signing credentials, an app record, and submission credentials. Choose the fixed bundle identifier above.
4. If submission requires an existing app record, create Cal Tracker in App Store Connect using the bundle identifier above. Set its numeric Apple ID as `ascAppId` in both `submit.testflight` and `submit.production` in `eas.json`.
5. In App Store Connect, open Cal Tracker → TestFlight. Create an internal testing group and install the `testflight` build for controlled testing. Internal testers must be eligible App Store Connect team members.
6. After testing, run `npm run build:production`. Both profiles produce the same app identity; production uses a separate update channel. TestFlight builds do not connect to a Metro development server.
7. Create an external testing group for the production build. Complete beta description, contact/feedback details, What to Test, and review information. Provide a working review account if login is required. Submit for Beta App Review, then enable a public invitation link once approved.
8. Testers install Apple's TestFlight app and accept the link. They need no Expo account, device registration, or Developer Mode.

If a build uploaded successfully but submission failed, avoid rebuilding unnecessarily:

```sh
npm run submit:testflight
# Or select the production binary:
npm run submit:production
```

Select the correct existing build when prompted. TestFlight is separate from publishing to the public App Store. Each binary expires after 90 days; upload another binary before expiry. OTA updates do not extend that deadline.

## Backend environment

Both store profiles and their updates use the EAS `production` environment, with these project-scoped variables:

- `EXPO_PUBLIC_SUPABASE_URL`
- `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`

These are public client configuration bundled into the app. They are stored with sensitive visibility to avoid casual dashboard/log exposure. OpenAI keys and Supabase secret/service-role keys remain exclusively on the backend. Never upload them as `EXPO_PUBLIC_*` variables.

Local development/export uses `.env`; cloud builds and update commands use the EAS environment. The iOS bundle identifier is not environment-dependent. The development and preview profiles use their own EAS environments; configure their public backend variables before building those profiles.

Use dedicated test users because controlled and public testing share the backend. Before distribution, verify email registration/confirmation, the deployed estimation function, and database access for those users. Backend schema changes must remain compatible with older installed binaries and cached SQLite data.

## Publish a JavaScript or asset update

Commit and validate the intended changes. Publish only from the intended checkout:

```sh
npm run typecheck
npm run lint
npx expo install --check
npm run export:ios
npm run update:testflight -- --message "Describe the change"
```

Install the binary built using the `testflight` profile. Open it online, allow the download, then fully close and reopen it to apply the update. Updates check on launch without blocking startup; downloaded updates normally take effect on a subsequent launch. Test offline launch as well.

After validation, copy the update group ID printed by EAS and promote that exact bundle:

```sh
npm run update:promote -- --group TESTED_UPDATE_GROUP_ID --message "Promote tested fix"
```

Production binaries receive the update; testflight binaries stay on their test channel. Do not switch an installed app's channel at runtime. For a direct, already-validated production publish:

```sh
npm run update:production -- --message "Describe the change"
```

Review downloads/crashes and feedback in the EAS dashboard and App Store Connect. To roll back, republish a known good update group with the same runtime:

```sh
npm run update:rollback -- --group KNOWN_GOOD_UPDATE_GROUP_ID --message "Rollback problematic update"
```

For the first OTA update, when no previous good update group exists, use `npx eas update:roll-back-to-embedded --channel production` and follow its prompts to select the affected runtime. Avoid rolling back database migrations that older code cannot read.

## When to rebuild

After an Expo SDK upgrade, regenerate the local native project with `npx expo prebuild --platform ios` before running `npm run ios`. Existing ignored native files may retain the old SDK template. In particular, SDK 57's `AppDelegate.swift` uses `internal import Expo`; a stale plain `import Expo` conflicts with the generated module provider and causes an ambiguous import access-level compiler error. Cloud builds generate the current template automatically.

The runtime version uses Expo's `appVersion` policy, initially `1.0.0`. JavaScript/layout/logic/assets can update compatible binaries without rebuilding.

Changes to native dependencies, Expo SDK, permissions, plugins, bundle identity, or native app configuration require a new binary. Increment `version` in `app.config.ts` (and align `package.json`), then build testflight and production again. EAS increments the iOS build number separately. Never publish code requiring new native functionality to an old runtime.

The encryption declaration is `usesNonExemptEncryption: false`: current code uses OS-provided HTTPS and secure storage, with no custom encryption implementation. Reassess if adding encryption libraries.

## Release verification

- Cloud builds currently use npm 10.9.8. After changing dependencies or running audit fixes, regenerate the lockfile with `npx npm@10.9.8 install --package-lock-only` and verify `npx npm@10.9.8 ci --include=dev`. Checking only the root lockfile entries misses nested peer dependencies; npm 11 can leave a lockfile that npm 10 rejects.
- Verify name, owner, bundle ID, project ID, update URL, and runtime in `npx expo config --type public`.
- Run `npx eas build:inspect --platform ios --profile production --stage archive --output /tmp/cal-tracker-release-archive` and ensure local `.env`, native directories, signing keys, and `node_modules` are excluded.
- On a physical iPhone, verify sign-up/sign-in, session restoration, manual entries, history, presets, goals, synchronization, offline edits, and camera/photo/text estimation.
- Confirm the app starts without a development server, including offline after initial sign-in/sync.
- Verify a testflight-channel OTA change, channel isolation, production promotion, and rollback.
- Verify an external tester can install the approved production build via its public invitation link.
